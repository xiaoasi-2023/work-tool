# 研发管理工作台：功能、字段与业务规则

版本：讨论稿 v1.1

日期：2026-11-07

适用场景：开发经理个人维护，每周五复盘本周进度、安排下周工作、更新项目实际投入。
当前状态：首版已实现，随 Workbench 0.2.0 提供。以下为原规划及业务口径，实际交付范围见文末说明。

已确认口径：

| 项目 | 确认规则 |
| --- | --- |
| 工时单位 | 实际投入统一录入小时，1人天固定按8小时换算；人天用于汇总展示和兼容原模板 |
| 录入粒度 | 按人员、角色和专项版本汇总登记即可，关联具体需求或任务可选 |
| 完成日期 | 指开发完成日期；提测、测试完成和实际上线日期分别记录 |
| 更新划分 | 按专项更新/版本划分，一个项目可以持续存在多个更新版本，不按周或月自动拆版本 |

界面建议统一使用“专项版本”名称；下文的“批次”均指该专项版本，用于对应现有投入模板的一行。

## 一、设计目标与日常工作量

模块放在现有 Workbench 中，继续使用本机桌面程序和本地数据库。

需要解决的问题：

1. 需求跨周、跨角色安排时，后续工作持续留在待办范围内。
2. 每周计划与实际结果能够对比，延期结转后保留原记录。
3. 开发、联调、测试、上线分别跟踪，能查清下一步和负责人。
4. 实际投入只登记一次，自动生成周汇总、迭代汇总和项目累计。
5. 保留现有排期表及投入统计表的导出方式，方便汇报。

日常最少操作：

- 新建需求：选项目、填标题、勾选涉及的工作类型，其他内容可后补。
- 安排工作：选任务、人员、周次，填本周预计工时。
- 周五复盘：更新任务状态，填本周实际投入、剩余工作及下一步。
- 系统完成：累计投入、计算人员负荷、生成关注清单、整理导出表。

不是每条需求都需要产品、前端、后端、联调、测试全部参与。新建时可以套用模板并取消不涉及的工作。

## 二、业务对象和关联关系

| 对象 | 一条记录代表什么 | 例子 |
| --- | --- | --- |
| 业务项目 | 一个长期管理的业务范围 | 4.0项目、经销商小程序 |
| 专项版本 | 项目的一次专项更新，也是投入模板的一行 | 报价模块v1.1、ES服务优化专项 |
| 需求/工作项 | 需要持续跟踪的一项功能、缺陷或其他工作 | 报价单增加客户信息 |
| 角色任务 | 需求中的一项具体职责或交付 | 小程序前端开发、后端接口、验收测试 |
| 周排期 | 某人在某周对指定任务范围安排的工作量 | 高正峰本周前端开发16小时 |
| 实际投入 | 某人在一个实际时间范围内投入的工作量 | 高正峰本周实际投入12小时 |
| 交付事件 | 一次实际发生的提测、验收、上线等事件 | 11月某日测试通过 |

主要关系：一个业务项目可有多个专项版本，每个版本可包含多条需求。同一版本可以持续多周，版本确定交付范围后关联需求；需求尚未确定版本时可以先留在项目需求池。需求可包含多个同类型任务，例如 PC 前端和小程序前端。

注意：

- 业务项目独立于现有 Git 项目。一个业务项目可选关联多个 Git 仓库，没有仓库也能使用管理功能。
- 周次是时间视图，不是需求的归属。需求不会因为切换到下一周而重新创建。
- 已经发生的排期、实际投入保留当时的项目和批次归属。调整需求的后续交付批次时，历史投入不会悄悄搬到新批次。
- 正常交付需求在上线前持续开放；调研、维护、会议等工作可选择“验收完成”作为结束条件。

## 三、页面与功能入口

| 页面 | 主要内容 | 高频操作 |
| --- | --- | --- |
| 管理总览 | 本周进度、下周负荷、待衔接工作、逾期和阻塞 | 打开需要处理的事项 |
| 需求台账 | 所有需求及各角色进展，可按项目、阶段、人员筛选 | 新建、拆任务、安排后续工作 |
| 周工作台 | 本周复盘、下周排期、未来排期、历史周记录 | 更新、结转、调整、确认、导出 |
| 投入统计 | 周投入、批次投入、项目累计、人员与角色分布 | 登记实际投入、查看明细、导出 |
| 基础资料 | 项目、人员、角色、工时标准、工作模板 | 维护基础选项 |

需求详情展示基本资料、角色任务、排期历史、投入明细、交付记录和变更记录。

沿用区域滚动：导航和操作区固定，列表、任务详情、投入明细分别滚动。

## 四、基础资料字段

### 4.1 业务项目

| 字段 | 必填时机 | 说明与规则 |
| --- | --- | --- |
| 项目编号 | 自动生成 | 用于稳定关联，改名不影响历史 |
| 项目名称 | 新建时 | 同一工作空间内唯一 |
| 项目负责人 | 可选 | 用于默认联系人和关注清单 |
| 项目状态 | 默认进行中 | 进行中、暂停、已归档 |
| 模块列表 | 可选 | 报价、MES、CAPP等，可持续补充 |
| 关联Git仓库 | 可选 | 可关联多个，不参与工时自动推断 |
| 备注 | 可选 | 项目说明 |

归档项目保留历史数据，默认不出现在新排期的选项中。

### 4.2 人员

| 字段 | 必填时机 | 说明与规则 |
| --- | --- | --- |
| 人员编号 | 自动生成 | 姓名变化不改变历史归属 |
| 姓名 | 新建时 | 同名时需要显示区分信息 |
| 默认角色 | 可选 | 产品、前端、后端、测试等，可多选 |
| 默认每周可排工时 | 启用负荷提醒时 | 建议初始40小时，支持人员差异，待确认 |
| 本周可用工时调整 | 有需要时 | 请假、会议、调休或值班后直接调整 |
| 状态 | 默认在职 | 停用后不能新增安排，历史仍可查询 |
| 备注 | 可选 | 不涉及账号或登录权限 |

人员角色表示默认能力；实际统计以每条任务、排期和投入记录的角色为准。同一人可以参与前端和后端工作。

### 4.3 公共设置

- 周次建议按周一至周日划分，周名称同时显示起止日期，避免“11月第1周”的歧义。
- 负荷按实际可用工时计算，默认值不等同于强制工作日规则，支持调休周。
- 1人天固定换算为8小时。日常实际投入只录入小时，人天由系统计算；历史模板中的人天按同一规则转为小时。
- 工作环节支持产品设计、前端开发、后端开发、联调、测试、上线、其他；可配置常用模板。
- 投入角色与工作环节分开。投入角色默认产品、前端、后端、测试、其他；联调和上线由谁承担，就归集到其实际角色，同时保留工作环节用于筛选。
- 复杂度可保留现有A/B/C分类。具体含义需确认，不自动换算成工时。

## 五、专项更新版本字段

每个专项版本对应现有《项目更新用时统计模板》中的一行，可以包含多条需求。一个项目有多次更新，就建立多个版本，分别记录范围、进展、日期与投入；周排期只引用版本，不生成新版本。

| 字段 | 必填时机 | 说明与规则 |
| --- | --- | --- |
| 批次编号 | 自动生成 | 内部关联和导入识别 |
| 所属项目 | 新建时 | 一个批次属于一个项目 |
| 版本标识 | 默认自动生成，可修改 | 如v1.1或专项编号，项目内唯一，用于区分多次更新 |
| 版本名称 | 新建时 | 如“报价模块客户信息优化”或“ES服务优化专项” |
| 模块/交付范围 | 可选 | 可关联多个需求，文字说明作为补充 |
| 批次负责人 | 可选 | 负责推进交付的人 |
| 计划开始日期 | 排期明确时 | 计划口径，不代替实际日期 |
| 计划完成日期 | 开发承诺明确时 | 指计划开发完成日期，用于判断开发延期 |
| 计划提测日期 | 测试安排明确时 | 与开发完成日期分开 |
| 计划测试完成日期 | 测试安排明确时 | 用于判断测试阶段延期 |
| 计划上线日期 | 需要上线时 | 支持与完成日期不同 |
| 实际开始日期 | 开发实际开始后 | 指本专项版本的开发开始日期，经理确认，作为开发自然日周期起点 |
| 实际完成日期 | 开发完成时 | 即开发完成日期，本次范围内必要开发任务完成后由经理确认；不等待测试或上线 |
| 实际提测日期 | 提测后 | 记录何时交给测试 |
| 实际测试开始日期 | 测试开始后 | 可选，用于区分等待测试和正在测试 |
| 实际测试完成日期 | 测试通过后 | 独立于开发完成日期；多轮测试保留各轮事件，当前字段显示最终通过日期 |
| 实际上线日期 | 实际上线后 | 需要上线的批次才填写 |
| 批次状态 | 系统汇总并确认 | 未开始、开发中、开发完成待衔接、联调中、待测试、测试中、待上线、部分上线、已上线；另有暂停/取消/归档标记 |
| 备注 | 可选 | 延期、范围变化或交付说明 |
| 预计总投入 | 可选 | 批次预算，和逐周排期总量分列展示 |
| 实际总投入 | 自动汇总 | 来自实际投入记录及期初投入，不可直接覆盖总数 |

版本的开发完成、测试完成与上线分别按本次有效范围判断。开发完成后仍保持后续跟踪，必要测试和上线未完成时不会自动归档。部分需求上线时显示“部分上线”，保留其余未上线需求。新增、移出或取消范围都留变更记录。

需求台账允许暂不指定批次；一旦要归集工时或正式确认周排期，应选批次，也可使用明确命名的日常维护批次。

## 六、需求/工作项字段

| 字段 | 必填时机 | 说明与规则 |
| --- | --- | --- |
| 需求编号 | 自动生成 | 跨周使用同一编号 |
| 标题 | 新建时 | 周表中的主要工作内容 |
| 所属项目 | 新建时 | 必须明确业务归属 |
| 当前交付批次 | 可后补 | 待需求范围或交付时间确定后选择 |
| 模块 | 可选 | 可从项目模块列表选择 |
| 工作类型 | 默认功能需求 | 功能、缺陷、优化、调研、运维、其他 |
| 需求端 | 可选 | PC、小程序、App、服务端、无界面等，可多选 |
| 优先级 | 默认普通 | 紧急、高、普通、低，待确认名称 |
| 需求负责人 | 可后补 | 负责整体推进与衔接 |
| 需求说明 | 可选 | 背景、范围、补充说明 |
| 验收条件 | 进入开发前补充 | 什么结果算本需求完成 |
| 外部编号/链接 | 可选 | TAPD、飞书或其他来源，首版作为引用保存 |
| 涉及工作类型 | 新建时选择 | 决定需要创建哪些角色任务 |
| 结束条件 | 默认实际上线 | 可选验收完成，适用于不需要上线的工作 |
| 当前阶段 | 根据事实建议、经理确认 | 需求确认、待开发、开发、联调、测试、待上线、已上线/已验收 |
| 开发完成日期 | 必要开发任务完成后 | 与测试、上线日期分开；只完成前端且后端仍有必要开发时，不填写整条需求的开发完成日期 |
| 提测/测试完成/上线日期 | 各事件实际发生后 | 可以从交付记录带出，允许补录并留痕 |
| 计划交付日期 | 有承诺时 | 对需求整体的目标，不因简单结转而自动延后 |
| 下一步行动 | 未结束时 | 如“安排后端接口”或“等待客户验收” |
| 下一步负责人 | 下一步明确时 | 可与需求负责人不同 |
| 下次跟进日期 | 有后续等待时 | 适合隔几周才安排的事项 |
| 暂停/取消标记 | 按需 | 必须填写原因；暂停保留原阶段和恢复后的下一步 |
| 创建/更新时间 | 自动记录 | 用于检索和变更追溯，不单独推断进展 |

整体阶段和角色任务分别展示。例如前端在开发、后端尚未开始，整体仍可处于开发阶段；下一步明确显示后端安排。

首版优先展示“当前阶段＋各任务状态＋剩余事项”。任务百分比只作辅助，整体不直接对各角色百分比取平均。

## 七、角色任务字段与状态

| 字段 | 必填时机 | 说明与规则 |
| --- | --- | --- |
| 任务编号 | 自动生成 | 与需求关联，跨周不变 |
| 所属需求 | 新建时 | 同一需求可有多个前端或后端任务 |
| 任务名称 | 默认按类型生成 | 可改为“小程序页面”“管理端接口”等 |
| 工作环节 | 新建时 | 产品设计、前端开发、后端开发、联调、测试、上线、其他 |
| 默认投入角色 | 正式安排时 | 产品、前端、后端、测试、其他；联调和上线按实际执行身份选择 |
| 主要负责人 | 正式安排时 | 负责推进；实际排期和投入可包含其他人员 |
| 复杂度 | 可选 | A/B/C或未评估 |
| 总预计工时 | 可选 | 对任务完整范围的估计，不和各周排期重复求和 |
| 执行状态 | 默认未开始 | 未开始、进行中、阻塞、已完成、已取消 |
| 进度百分比 | 可选 | 未开始为0，已完成为100，进行中可手填1至99 |
| 剩余预计工时 | 复盘时建议填 | 用于后续排期；由人评估，不用总估时减实际投入强行得出 |
| 前置任务 | 有依赖时 | 可关联其他任务，禁止循环依赖 |
| 计划完成日期 | 有承诺时 | 用于提醒；变更时保留原值和原因 |
| 实际开始/完成时间 | 状态变化时记录 | 允许补录实际日期，补录留痕 |
| 阻塞原因 | 阻塞时 | 应说明缺少什么，以及谁负责解除 |
| 本周进展说明 | 复盘时 | 如“页面完成，等待接口” |
| 验收说明/链接 | 完成时可填 | 对接结果、测试记录等 |

执行状态与排期标签分开：

- 执行状态描述事情做得怎样。
- 排期标签由安排自动得出：未排期、本周有安排、未来有安排、待续排。
- 任务未完成，且本周结束后没有未来安排时，进入待续排清单。
- 不涉及的角色不创建任务；必要任务不能通过随意取消来让需求完成，取消或改变必要范围需要说明原因。
- 已完成任务允许重新打开，要求填写返工原因。实际投入保留；受影响的提测、验收或上线状态提示复核，历史交付事件仍保留。
- 已上线后新增的缺陷建议新建关联缺陷项，关联原需求和新的处理批次，保留原交付事实。

依赖用于提前提示和检查。确有部分联调、提前测试等情况时，可记录范围和原因后继续安排，避免把正常并行协作完全锁死。

## 八、周排期字段与规则

### 8.1 一条周排期的定义

一条周排期代表：一个人在一个自然周，对某项目、某批次、某角色的一项或一组任务安排了多少工作。

同一任务可以跨多周、多人参与。每个人分别有自己的预计工时。

| 字段 | 必填时机 | 说明与规则 |
| --- | --- | --- |
| 排期编号 | 自动生成 | 不随周表排序变化 |
| 所属周 | 新建时 | 存周起始日期，界面显示起止日期 |
| 项目、批次 | 确认计划时 | 从任务带出，批次不能为空 |
| 工作范围 | 新建时 | 关联一个或多个角色任务 |
| 投入角色 | 新建时 | 由关联任务带出，可按实际执行身份确认 |
| 执行人员 | 确认计划时 | 一条记录对应一个人 |
| 本周工作目标 | 确认计划时 | 例如“完成页面，接口本周不接入” |
| 本周预计工时 | 确认计划时 | 单位小时，允许小数；预排时可以暂缺 |
| 周内计划起止日期 | 可选 | 首版不强制细化到每天 |
| 工作来源 | 自动或选择 | 原计划、跨周结转、临时插入 |
| 计划状态 | 默认草稿 | 草稿、已确认、已撤销 |
| 本周结果 | 周复盘时 | 未开始、部分完成、已完成本周目标、阻塞、撤销 |
| 本周进展/延期原因 | 按需 | 解释预计与实际的差异 |
| 后续处理 | 未结束时 | 结转到下周、安排未来周、退回待排、暂停、取消 |
| 本周实际工时 | 自动汇总或快捷登记 | 快捷登记也写入实际投入记录，不产生另一套总数 |
| 来源排期编号 | 结转时自动记录 | 用于查看连续多周的演变 |

“本周目标完成”与“任务整体完成”分别处理。例如任务要做三周，本周目标完成后，整体仍可以进行中。

### 8.2 共用工时：兼容截图中的合并单元格

截图中存在一个8小时覆盖多项工作的情况。建议保留为一条“组合排期”，关联多条角色任务。

- 预计工时存放在排期记录上，整个组合只计算一次。
- 组合中的任务必须属于同一项目、批次、工作环节和投入角色；同一排期只有一个执行人员。
- 多人参与时分别记录每个人的预计工时。
- 各需求进展仍独立更新，不要求所有子任务进展一致。
- 组合投入可以保留为整组投入；未分摊时不展示虚构的单需求成本。
- 后续需要精确分摊时，采用替换分配并核对总额，不能在已有整组工时之上再次增加明细。
- 一个任务在同一周、同一人员下同时被单独排期和组合排期覆盖时，提示重复安排，确认原因后才允许保存。

### 8.3 人员负荷

本周已确认排期总工时 ÷ 本周可用工时 = 本周计划负荷。

草稿和已确认计划分列展示；人员可用工时为0时显示“无可用工时”，不进行除法。超量给出提醒，经理可确认安排；不限制实际投入登记。

## 九、实际投入字段与统计口径

### 9.1 录入方式

首版支持按周登记，默认预填本周和人员，不要求每天打卡。日常按“周＋项目＋专项版本＋人员＋角色”汇总实际小时，关联需求、任务或排期可选，不要求把总投入逐条拆到需求。

两种入口使用同一份投入明细：

1. 周排期上直接填写本周实际工时。
2. 投入页面登记未排期的工作，或补充与具体任务无关的维护投入。

输入框再次填写表示修改这一条记录的实际数值。例如由8改为10，累计增加2，不是再追加10。额外增加投入使用明确的“新增记录”操作。

| 字段 | 必填时机 | 说明与规则 |
| --- | --- | --- |
| 投入记录编号 | 自动生成 | 去重、编辑和追溯的依据 |
| 项目、批次 | 保存时 | 是项目成本归属依据 |
| 人员 | 保存时 | 每人单独记录，可批量填写 |
| 角色 | 保存时 | 产品、前端、后端、测试等；允许同一人承担不同角色 |
| 工作环节 | 默认从关联任务带出 | 可单独查看联调、测试、上线等工作的实际投入，不重复计入另一角色 |
| 实际所属周 | 保存时 | 统计归属周，不是录入操作发生的周 |
| 实际覆盖日期范围 | 默认整周 | 有期初分界或补录时可细化 |
| 实际投入小时 | 保存时 | 统一录入小时，非负，支持小数 |
| 换算人天 | 自动计算 | 实际小时除以8，不要求另外填写 |
| 原始导入单位及数值 | 历史导入时保存 | 兼容原模板的人天输入，按8小时换算并保留来源用于核对 |
| 关联排期 | 可选 | 从排期入口登记时自动带出 |
| 关联任务 | 可选 | 可以关联单项或组合范围，未分摊时只做范围说明 |
| 投入类型 | 默认正常工作 | 正常、返工、临时支持、其他，可选 |
| 工作说明 | 按需 | 无关联任务、补录或修改时建议说明 |
| 来源 | 自动记录 | 手工、排期快捷录入、历史期初导入 |
| 创建/修改记录 | 自动保存 | 保留修正前后的数值与原因 |

### 9.2 计算规则

- 周投入：汇总实际归属在该周的投入记录。
- 批次投入：汇总该批次的期初投入和后续实际投入。
- 项目投入：汇总项目下各批次实际投入，不能再叠加一份独立手填项目总数。
- 角色投入：按实际投入记录中的角色汇总。
- 人员投入：按人员编号汇总，改名不影响累计。
- 人天：实际小时除以8；小时作为统一录入及核对口径，内部使用定点精度避免长串小数误差。
- 开发自然日周期：开发完成日期减开发开始日期加1，不因等待测试或上线而继续增加。开发未完成时最终周期留空，可单列开发已历时天数。
- 测试周期和开发完成至上线的间隔独立展示，名称与开发周期区分；需要两个实际日期才能计算，不用排期工时推断。
- 开发完成不冻结版本实际投入。测试、上线和返工等仍可登记到同一版本，按角色及工作环节单独查看，并计入该版本实际总投入。
- 实际工作量允许超过预计工时；超出只提示差异，不截断实际数值。
- 空值表示尚未填写，0表示确认没有投入；完成任务不会自动把预计工时填成实际工时。
- 同一笔实际投入不能同时作为整组总额和子任务明细参与求和。

预计总投入、本周排期、实际投入是三个不同指标。系统分别展示，不把它们相加。

### 9.3 现有累计数据的导入

现有模板按专项版本和角色填累计人天，不一定能还原每周明细。导入时人天乘8转为小时，作为期初数据保存：

1. 选择截至日期，并预览项目、批次、人员、角色和累计投入。
2. 没有周次证据的历史累计只进入累计报表，不能自动分摊到各周。
3. 此后录入截至日期之后的新投入，系统将两部分累计。
4. 截至日期落在周中时，首周新增记录明确覆盖日期，避免包含已计入期初的时间。
5. 重复导入同一范围是核对或替换期初，不再次累加；更改截至日期且与已有投入交叉时必须先核对范围，首版阻止直接叠加。

历史期初单独保存，允许只到角色或共同人员组；这类未分摊数值可以计入批次、项目累计，但不虚构个人或周明细。日常新增投入仍要求明确到人员。

## 十、阶段推进、测试与上线

常规交付路径：需求确认 → 开发 → 联调（如需）→ 测试 → 待上线 → 已上线。

| 事件/变化 | 系统处理 |
| --- | --- |
| 产品方案完成 | 提示安排必要的前端、后端等任务；已有未来安排时显示具体周次 |
| 必要开发任务完成 | 提示确认开发完成日期，再根据需要安排联调或提测；不等待测试才记录开发完成，也不直接认定已上线 |
| 联调完成 | 提示测试负责人、目标日期和当前安排 |
| 提测 | 记录提测时间、范围和负责人 |
| 测试不通过 | 记录问题与下一负责人，允许重新打开相关开发任务，已有投入不清零 |
| 测试/验收通过 | 单独记录测试完成日期，具备上线条件时进入待上线，不覆盖开发完成日期 |
| 实际上线 | 填上线日期、范围和结果，经理确认后记录为已上线 |
| 上线失败/回滚 | 保留本次事件，记录原因和后续处理，不能继续显示为当前已成功上线 |

建议保留的交付事件字段：需求/批次、事件类型、实际时间、负责人、范围、结果、说明、附件或外部链接。

“完成日期”已确定为开发完成日期。提测、测试开始、测试完成、实际上线分别保留独立日期；开发完成后等待测试、上线的自然时间不混入开发周期。

测试退回时记录返工任务及其开始、完成时间和实际投入，保留原开发完成事件。确需修正版本开发完成日期时由经理明确修改并留痕，系统不因开始测试或返工而静默覆盖已有日期。

不需要测试或上线的工作，可按选定结束条件完成。跳过必要阶段、部分提测或部分上线时明确范围和原因，避免误关整条需求。

## 十一、跨周结转与周记录

### 11.1 周五复盘流程

1. 打开本周视图，查看本周原计划和临时插入工作。
2. 更新本周目标结果及任务整体状态，登记实际投入。
3. 对未结束事项选后续处理，可用批量结转，但逐项显示预览。
4. 在下周视图确定人员、本周目标和剩余预计工时，检查人员负荷。
5. 检查无后续安排、待提测、待上线和逾期事项。
6. 确认本周结果和下周计划，再导出汇报。

### 11.2 结转规则

- 原周记录保留，包括原预计工时、本周结果和实际投入。
- 新周创建新的排期，关联同一个任务及来源排期编号。
- 实际投入不复制；新周实际工时默认为未填写。
- 新周预计工时由经理确认剩余工作后填写，不盲目复制原预计工时。
- 原需求或任务的承诺日期不会因结转自动改变；需要延期时单独记录新的预计日期和原因。
- 未来周已有同人同范围安排时，提示合并或保留，避免重复结转。
- 原周未完成不一定就是延期：任务本来计划跨多周、本周目标完成时应显示正常跨周。

### 11.3 历史周口径

周工作台分为实时视图和已确认版本：

- 实时视图反映当前任务事实。
- 确认版本保存当时的计划、阶段、进度说明、人员和统计数值。
- 后来任务完成，不会把上周保存的“进行中”改成“已完成”。
- 历史补录或修正保留记录；需要重发周报时生成新修订版本，原版本仍可查看。
- 新确认的周报显示补正提示，避免实时投入和历史报表版本被误认为完全同一口径。

## 十二、关注清单与提醒规则

| 关注项 | 触发条件 | 处理方式 |
| --- | --- | --- |
| 下一角色待安排 | 前置工作具备条件，必要后续任务无有效安排 | 安排人员和周次，或写明等待原因与跟进日期 |
| 待续排 | 任务未结束，本周后没有未来排期 | 结转、安排未来、退回待排或暂停 |
| 开发完成待衔接 | 必要开发完成，联调/提测没有下一步 | 确认后续任务和负责人 |
| 测试通过待上线 | 已验收，需上线但尚无上线记录 | 安排上线负责人和日期 |
| 阶段逾期 | 开发、测试或上线超过各自计划日期，且该阶段尚未完成 | 按对应阶段提示；开发已完成但仍在测试时，不再计为开发逾期 |
| 已到跟进日期 | 到达下一次跟进日期且需求未结束 | 确认进度并设置新的下一步 |
| 长期阻塞 | 阻塞超过设定阈值 | 明确解除阻塞的负责人和处理日期 |
| 排期超量 | 已确认工时超过人员本周可用工时 | 调整或记录超量安排原因 |
| 实际投入未填写 | 周复盘中有开展工作但实际数值仍为空 | 补填或明确为0 |

阈值可配置。已明确安排在三周后的任务显示未来安排和跟进日期，不每天重复当成漏排。

首版提醒以应用内关注清单为主，打开模块时重新计算。关闭程序后的系统提醒需要另行增加后台运行能力，不作为首版已经具备的能力。

## 十三、导入、导出与数据保护

### 13.1 工时模板导入

- 读取当前模板的项目、模块功能、开始/完成日期、各角色人员与人天、实际上线日期和备注；开始/完成日期按开发日期映射，人天按8小时转为实际小时。
- “模块功能”在导入预览中建议映射为批次名称，不强行拆成单条需求。
- 人员1、人员2映射成多个人员投入记录；数据模型不限制每个角色只能有两个人。
- 一个人员格包含多个人名、一个数值又是共同总额时，先保留为待分摊的角色历史总额。没有证据时不能均分或给每个人重复记全额。
- 空白、公式占位和示例数据不作为真实投入记录导入。
- 人员重名、项目同名、同批次已有期初等情况在预览中解决，再统一确认写入。
- 日期无效、完成早于开始、工时负数、缺少归属时反馈具体行，不静默猜测。
- 导入前备份；整批导入使用事务，失败回滚；导入批次有记录可追溯。

### 13.2 周排期导入

首版优先保证新建和导出好用。兼容旧周表的导入作为后续增强，需要原始导出Excel中的单元格和合并范围信息；截图用于确认样式与含义。

工时合并格必须在预览中确认其覆盖任务，保存为组合排期，不能向每行复制同一个工时。跨项目或跨批次的共同工时要求人工拆分后再确认。

### 13.3 导出

- 周排期表：按你现有的项目、需求端、阶段、工作内容、各角色复杂度/工时/人员/状态整理，显示周起止日期。
- 本周复盘表：增加本周目标结果、实际工时、剩余工作和延期原因。
- 投入统计表：保持每个项目每个专项版本一行，主表输出实际小时；兼容原模板时输出按8小时换算的人天。开发开始/完成、提测、测试完成、上线日期分别列出，原“完成日期”对应开发完成。
- 人员超过模板现有两列时，按实际情况扩列或使用附属人员明细，避免遗漏。
- 组合工时导出为共享分组；不能为了铺平表格而在汇总时重复计算。
- 导出确认版本或实时数据时标明所用口径。

### 13.4 本地数据

数据继续保存在本机用户目录，和安装目录分离。新增结构通过数据库版本迁移创建；迁移、导入前自动备份，提供手工备份与恢复入口。

项目、人员、批次有历史引用后采用归档/停用；不物理删除历史成本。实际投入修正、状态回退、批次变更、历史周补正均记录前后内容、操作时间和原因。

## 十四、完整场景示例

假设有需求“报价单增加客户信息”，归属“4.0项目 / 报价模块v1.1专项更新”，1人天固定按8小时：

1. 新建需求时选前端、后端、联调、测试、上线；产品方案已完成可补记完成事实。
2. 前端本周排16小时，后端预排三周后8小时，保存下一次跟进日期。
3. 周五前端实际投入12小时并完成。系统保存12小时，可展示换算为1.5人天；后端未来安排仍清晰可见。
4. 此时整体需求尚未交付，不进入已上线统计；关注清单显示等待后端及其安排周。
5. 后端当周实际完成5小时、工作尚未结束，经理估计还需4小时，确认转入下一周。原周保留预计8、实际5、部分完成，新周预计4、实际空。
6. 后端下一周实际4小时完成，后端累计9小时；不会变成8+5+4=17小时。本次范围内必要开发任务完成时确认开发完成日期。
7. 联调、测试分别登记实际小时及结果。测试不通过时记录返工任务，之前工时与开发完成事件保留。
8. 提测后填提测日期，测试通过后填测试完成日期，上线后再填实际上线日期，三者都不替代开发完成日期。
9. 批次汇总自动包含各需求和正常返工的实际投入；周报展示每周事实，历史确认版本不随最新阶段变化而重写。

## 十五、首版范围与业务口径

### 首版必须具备

- 项目、人员和批次基础资料。
- 需求台账、角色任务及下一步跟踪。
- 周排期、人员负荷、组合工时、跨周结转和确认版本。
- 实际投入登记与项目/批次/角色/人员汇总。
- 应用内关注清单。
- 现有累计工时模板预览导入、周表和投入表导出。
- 数据备份和关键变更记录。

### 后续增强

- 复杂旧周表的批量导入与分组识别。
- 甘特图、每日细排、更多趋势图。
- 飞书或TAPD同步、多人在线填报。
- 程序关闭后的后台提醒。

### 已确认的业务口径

1. 实际投入统一填小时，1人天固定等于8小时。
2. 按人员、角色和专项版本汇总登记，具体需求/任务关联可选。
3. 完成日期指开发完成，测试相关日期和实际上线日期另列。
4. 更新按专项版本划分，一个项目可以有很多个版本，同一版本允许跨多周。

### 其余可调整的建议默认值

- 联调、上线作为工作环节，投入按执行人的产品/前端/后端/测试等角色汇总；需要时增加运维等角色。
- A/B/C复杂度沿用现有表格，不自动决定工时，等级含义待补充。
- 人员默认周可用工时建议40小时，可按人员和实际周次调整；1人天8小时不自动代表每周必须工作5天。

其余字段通过默认值和逐步补填控制维护成本。
