# 研发管理功能与业务逻辑

核对日期：2026-11-08。本文描述当前代码已实现的行为，供日常维护和后续调整使用。

## 1. 数据保存与备份

研发管理目前由经理在本机维护，没有登录、云端数据库或远程协作服务。

| 运行方式 | 当前数据 | 备份位置 |
| --- | --- | --- |
| 浏览器调试 | 项目目录下 `.runtime/browser-data/management.json` | 同目录下 `management-backups` |
| 安装版 | Electron 用户数据目录下 `workbench.sqlite` | 同目录下 `management-backups` |

浏览器模式由本机服务读写文件，Chrome、Edge 和内置浏览器访问同一个服务时使用同一份数据。它已经不是每个浏览器各存一份。安装版与浏览器版的数据仍独立，可通过 JSON 备份迁移。Windows 安装版的用户目录通常是 `%APPDATA%/workbench-toolbox`，实际路径以界面显示为准。

顶部“备份记录”提供：

- 当前数据文件和备份目录。
- 按时间倒序分页的 JSON 备份记录，每页 10 条。
- 备份时间、文件名、手动/自动/历史来源、原因、数据修订号、文件大小，以及项目、需求、排期、投入记录数量。
- 立即备份、下载指定备份、导入备份文件、恢复到指定备份。
- 损坏或不符合数据规则的备份显示异常信息，禁止恢复。

恢复需要确认，服务会先保存当前数据，再用备份替换研发管理业务数据。修订号继续递增，保留恢复操作的审计信息；不会把 Git 项目、收藏、设置一起覆盖。跨浏览器有其他修改时，过期修订号的恢复会被拒绝。

批量修改、删除记录、清理需求内容/历史、重命名或删除模块、通过需求保存接口调整项目/版本归属，以及恢复之前，会自动生成备份。导出当前 JSON 也会保留一份本地记录。首次在已有 SQLite 中启用研发管理时，另保留旧数据库副本；这种 SQLite 副本不在 JSON 恢复列表中展示。

目前没有定时备份、云端备份或自动清理旧备份。备份与原数据都在本机，重要节点可下载到其他位置保存。备份恢复文件上限为 30 MB。

## 2. 数据之间的关系

| 对象 | 用途 | 关系 |
| --- | --- | --- |
| 项目 | 长期业务归属，例如 4.0项目、经销商项目 | 包含模块、专项版本和需求，与 Git 仓库目录独立 |
| 模块 | 功能分类，例如报价模块、微信小程序 | 由所属项目维护，需求关联可留空 |
| 专项版本 | 一次专项更新或发布范围 | 属于一个项目，可包含不同模块的需求 |
| 需求 | 持续跟踪的一项功能或独立事项 | 必须属于项目，可选择模块和专项版本 |
| 角色任务 | 谁以什么角色完成需求中的哪部分工作 | 属于一条需求，例如前端开发、后端开发、需求设计、测试 |
| 周排期 | 某人在某周准备做什么、预计多少小时 | 属于项目和专项版本，可关联角色任务 |
| 实际投入 | 某人在某周实际做了多久 | 属于项目和专项版本，关联排期、任务可选 |
| 周总实际投入 | 核定某人一周总共工作多久 | 独立于排期容量，记录确认值或历史标准周回填值 |
| 期初投入 | 历史累计工时，没有逐周明细时补录 | 计入版本累计，可选关联具体任务 |
| 周确认快照 | 固定当时的周报及相关数据 | 与实时数据分开，后续编辑不会覆盖 |
| 变更记录 | 保留变更前后内容、时间和原因 | 用于追溯，与业务投入分开 |

模块和版本是两个维度：模块回答“属于哪块业务”，版本回答“纳入哪次更新”。同一条需求跨周一直保留，每周增加或修改工时，不需要重复创建需求。

## 3. 项目、模块、人员和专项版本

### 项目与模块

项目包含项目编号、名称、负责人、模块、状态和备注。项目编号为空时生成 `PRJ-0001` 这种编号，也允许手填；项目编号不能重复。

模块单独维护，列表显示模块和需求数量，不再用一段多行文本维护。重命名会同步关联需求；删除有关联需求的模块时，需要确认影响范围，并将需求转入其他模块或取消模块关联。删除模块不删除需求和工时。关联需求在确认期间发生变化时，服务拒绝使用旧的确认范围删除。

项目和专项版本目录中的移除操作目前采用归档，人员采用停用，历史排期和投入保留。归档不等于彻底删除；部分历史查询下拉仍可能显示归档记录。

### 人员

人员包含姓名、角色、每周可用工时、排序、启用状态和备注。一个人可以同时有前端、后端等角色；角色表示本次工作的性质，不限制人员只能做一种工作。

人员排序影响周表和导出顺序。通常维护为赵浩程、曹鑫哲、常天翼、高正峰、刘宇、蒋世彤。默认每周可用工时可按人员维护，也可以在周排期里单独修改某一周的容量，用于请假、支持工作等情况。

### 专项版本

专项版本包含所属项目、标识、名称、负责人、范围、备注和状态，以及以下里程碑：

- 计划开始、计划开发完成、计划测试完成、计划上线。
- 实际开发开始、开发完成、提测、测试开始、测试完成、实际上线。
- 版本预计工时。

开发完成、测试完成、上线分别记录。投入统计优先显示明确填写的日期；没有版本日期时，可从需求、开发任务、测试任务和实际工作周汇总。只有周次的数据会显示周范围，不推算成某个具体完成日。开始和完成日期都明确时，开发周期按自然日计算；只有周次时显示跨几周，不当作投入人天。

## 4. 需求跟踪

### 基础字段与编号

需求包含需求编号、名称、所属项目、专项版本、模块、需求端、类型、优先级、负责人、说明、验收标准、外部链接、备注、交付日期及下一步跟进信息。

已有名称中可识别的 TAPD、销售等编号可提取到编号字段，名称去掉对应的编号片段；没有编号时生成 `REQ-000001` 这种编号。编号保持唯一，编辑名称或转移项目时不自动换号。历史批量编号补齐属于数据维护，不会把需求复制一份。

筛选包括名称/编号、项目、版本、模块、当前阶段和排期表现。需求列表、详情分别显示角色负责人、角色投入、计划/实际周次、预计/实际时长以及工作进度。

### 角色任务

新增需求时可选择创建需要的工作环节；后续可以增加、编辑任务。支持原型设计、文档、前端、后端、联调、测试、上线和其他环节。每个任务维护：

- 任务名称、角色、环节、负责人、任务复杂度。
- 预计小时、剩余小时、完成百分比、任务状态。
- 计划开始周、计划完成周、实际完成周，以及可选的具体开始/完成日期。
- 前置任务、阻塞原因、备注。

前后端负责人及投入分别展示。全栈人员可同时承担两种角色，但同一份投入只能统计一次。产品设计、文档、测试可以作为独立需求维护，产品总投入不必再重复分摊到每个开发需求。

### 三种状态口径

| 口径 | 回答的问题 | 示例 |
| --- | --- | --- |
| 需求阶段 | 目前走到哪个业务阶段 | 待开发、开发中、开发完成、测试中、待上线、已上线 |
| 周目标结果 | 这一周定的目标完成了吗 | 未开始、部分完成、本周目标完成、阻塞 |
| 排期表现 | 相对原计划是提前还是延后 | 提前完成、按期完成、延期完成、逾期未完成 |

“本周目标完成”可能只完成了一个阶段，不等于整个需求开发完。开发需求的前后端等有效开发任务都完成后，开发才算完成，完成周取较晚一方；测试和上线不影响开发提前量。只有产品或测试任务的独立事项全部完成时，可直接显示“已完成”，不会仍落入“待开发”筛选。

更新角色任务的整体完成情况时，会联动相关需求完成周和符合条件的周排期结果；组合任务未全部完成时保留部分完成。历史已完成事项可以直接补计划周、完成周，无需为了登记完成再创建周工时。

## 5. 计划周、实际周和工时比较

### 周次

内部用周一日期保存周次，页面通常显示周一至周五范围，例如 `11/02–11/06`。实际投入的周内覆盖日期可以延伸到周末。

确认排期时保留原计划周和原预计工时。调整当前执行周、当前预算不会自动改掉原基准。修正已建立的原计划需要填写原因，变更记录保留前后内容。

需求层若明确填写计划周，优先使用需求字段；否则汇总相关角色任务的计划周。角色任务可有各自的排期，因此后端提前、前端未做时，不会把整条需求算成已完成。

实际工作周来自已登记投入；没有投入明细时，可用已知任务开始/完成信息辅助展示。实际工作周表示发生过工作，实际完成周表示整体完成，这两个字段不能相互替代。

### 时间偏差

| 情况 | 判断 |
| --- | --- |
| 提前完成 | 实际完成周早于计划完成周 |
| 按期完成 | 实际完成周等于计划完成周 |
| 延期完成 | 实际完成周晚于计划完成周 |
| 逾期未完成 | 当前周已超过计划完成周，且仍未完成 |
| 提前开展 | 还没完成，但首次实际工作周早于计划开始周 |
| 待补录 | 已完成，但缺少可比较的计划周或完成周 |

同一周内早一天或晚一天，目前都按同周完成处理。需求和排期列表用文字、徽标及行样式区分表现；周报状态使用“已完成”“已完成（提前）”等文字。

### 工时偏差

预计与实际按小时比较，`1 人天 = 8 小时`。完成后实际小于预计才显示节省；进行中的剩余预算不算节省。实际超过预计会显示超时，但不因此判定交付延期。

例如计划 `11/09–11/13` 做 16H，实际 `11/02–11/06` 用 8H 完成，则是提前 1 周，节省 8H。若同周用 20H 完成，仍是按期完成，但比预计多 4H。

没有登记的工时显示“未登记”或 `—`，与明确登记的 0H 不同。组合工时不自动均分到每条需求；若无法得出可靠的单项预算和实际值，会保留组合口径，避免把整组工时重复算给每个成员。

## 6. 周排期与周五复盘

周排期提供“本周复盘”“下周计划”“排期管理”三个视图，可以切换任意周查看，也可继续安排更远的未来周。

### 安排工作

排期包含项目、版本、人员、角色、环节、执行周、关联任务、标题、预计小时、目标、来源和备注。本周目标可为空，简单任务直接用需求名称展示；产品需求设计等汇总事项可以补充本周具体功能和各项工时。

排期可保存草稿；确认排期需要人员和预计工时。草稿展示出来，但不计入已确认负荷。新建或扩大的组合排期最多关联 5 项任务，要求角色、环节和归属匹配。一个组合只有一份预算，不为每个需求重复累计。

未完成工作可以结转到未来周：保留来源，新建草稿并重新确认剩余预计小时；原周实际投入不复制，原计划基准仍可追溯。

### 本周复盘

本周实际以发生在所选周的实际投入为主，包括原计划未来做、这周提前完成的工作。已完成但没有本周工时的任务仍可列出，时长显示未登记，不用预计时长冒充实际时长。

保存复盘时可同时维护实际工作周、实际小时、具体工作内容、周目标结果，并勾选哪些角色任务已全部完成。工时、排期结果、角色完成情况作为一批数据保存，失败不只保存其中一部分。

需求里的周累计记录与投入明细使用同一份数据。同一条任务在同一人员、同一周已经有记录时，修改原值，不另加一份。周工作内容按发生周保存，不会随以后修改目标而改写历史。

### 核对周工时

只有人员周总实际投入和额外任务实际用时、缺少原计划逐项实际用时时，可以通过“核对周工时”录入一次周总量。周总实际投入不等同于人员容量，支持请假周、加班周和零投入周，不固定限制为40H。

已知任务实际用时锁定；剩余投入 = 周总实际投入 - 已知实际用时，再按原计划的原预计小时比例分配。组合投入仍是一笔，只分配到组合，不复制给成员。没有原预计时，旧分摊权重或原登记小时可作为权重。新候选排期需核对是否在本周发生过实际工作；未来未开展工作和以前周已完成的排期不会自动补入。

核对弹窗默认保留已有实际投入，包括没有来源标记的旧记录；只有明确标为分摊的记录默认重新分配。旧记录缺少标记不会被当成0H或自动覆盖，需重新分摊时可以逐项切换处理方式。周总投入优先取已核定值；尚未核定且本周事项均有登记实际时，取登记合计，避免用40H容量覆盖实际32H、48H或0H。没有完整实际登记时才以人员当周容量作为待核对的初始值。

例如本周原计划40H、额外提前任务已知16H、周总实际40H，则保留提前任务16H，原计划事项分摊24H。不会把实际投入登记成56H，也不会按比例缩减已知提前的16H。原预计、计划周、完成周及提前状态均保留。已知实际超过周总投入、余额存在但没有可分摊事项或权重时，拒绝保存。

分摊记录标明“分摊工时”，不代表每项实际测量。需求每周投入、排期时长、周报预览和投入明细同步显示来源。重新核对替换已有投入；只改进度或备注不改变来源，手动改小时则转为实报。后续修改投入导致合计与核定总量不符时，人员栏显示“待重新核对”。

历史按标准工作周回填的总量明确标注，区别于经理确认值。周总投入、核算备注和分摊来源进入JSON备份及新确认快照；旧快照没有核算数据时，不混入当前核算值。

### 下周计划与排序

下周待执行内容和已提前完成内容分开；提前完成不再占用下周待执行负荷。组合中只有部分提前完成时，会提示核对剩余工时，不自动平均拆分预算。

正常工作在前，已完成（提前）的工作放后，两部分分别按人员排序。同项目、模块、需求端、阶段和参与人员匹配的提前完成事项可合并展示，工作内容仍逐项保留名称及编号。

右侧人员负荷显示已确认计划小时、该周容量和负荷比例。这个比例是排期容量提示，不是人员绩效或奖励金额。

## 7. 周工作表导出

周报 Excel 包含“本周实际”“下周计划”“周报汇总”“工时核对”四个 sheet。可以从实时数据导出，也可以选择已确认的历史版本导出。

| 字段组 | 本周实际 | 下周计划 |
| --- | --- | --- |
| 公共字段 | 序号、项目、需求端、阶段、工作内容 | 相同 |
| 前端 | 任务复杂度、排期（H）、人员、状态 | 任务复杂度、排期（H）、人员 |
| 后端 | 任务复杂度、排期（H）、人员、状态 | 任务复杂度、排期（H）、人员 |
| 产品经理 | 任务复杂度、排期（H）、人员、状态 | 任务复杂度、排期（H）、人员 |

本周实际共 17 列，下周计划共 14 列，不带状态列。两者表头都沿用既有周表样式。本周实际的“排期（H）”放所选周实际小时；下周计划同名列放预计小时，不能把两者都当成累计投入。

设计、文档、测试在产品经理列组中分别成行，仍保留实际角色和工作环节。组合工作列出每条需求，工时通过合并单元格表示；同一份源工时在合计及人员汇总中只算一次。提前完成事项按上述项目与人员等维度归并，长内容拆行以保持可读。工时核对 sheet 保留来源明细供检查。

分摊结果保持原有17/14列表头和数值格式，来源写入工时单元格批注和“工时核对”的说明列。版本投入导出的“实际投入明细”在现有来源列标明分摊工时。

## 8. 投入统计与期初

投入统计分为版本投入、实际投入、期初投入。

版本累计小时 = 实际投入记录之和 + 期初投入之和；人天 = 累计小时 / 8。预计工时、完成百分比和排期记录不直接进入实际累计，新增排期不会增加项目实际投入。

版本按产品、前端、后端、测试、其他角色汇总，产品中另列原型设计、TAPD文档和未细分。产品分项包含在产品合计中，不额外加一次。导出还可按版本和人员汇总。

实际投入维护人员、周、小时、角色、环节、工作类型、覆盖日期、排期/任务关联、备注。允许只按人员和版本汇总，也允许关联具体任务。相同范围不能既登记一笔汇总，又登记任务明细；组合整体和子项也不能重复计时。

期初仅用于历史已有总时长、缺少逐周明细的情况。已经有需求下的周工时，不应再为相同工作新增期初。期初计入累计，但不会被虚构到某个周的周累计里；如与新投入处于同一周，须明确新增投入的覆盖日期晚于期初截至日期。

“导入历史投入”支持原项目更新用时模板，先预览再选择截至日期，人天按 8H 换算。共同人员总投入不会自动均分；同范围、同截至日再次导入更新原值。当前没有把任意小程序/后台排期 Excel 自动导入的通用入口，之前这类数据通过专项整理录入。

## 9. 总览、提醒和跟进

总览显示进行中需求、本周排期与计划小时、本周实际投入、下周已排，以及待跟进事项和进行中的专项版本。

提醒包括：到跟进日期、需求或任务截止日期逾期、阻塞、前置条件已满足但没有后续安排、开发完成待衔接、测试通过待上线、开发返工需复核，以及人员负荷超量。

周五至周日会增加本周未完成待续排、排期结果待复盘、实际投入未填写等提醒。提醒只在程序内显示，不在应用关闭后发送通知。

目前总览部分提醒按具体截止日期和明确填写的里程碑判断；需求/周排期的提前延期按周比较。这两处不是完全同源，周次已补齐但具体里程碑尚未填写时，仍可能需要核对总览提醒。

## 10. 历史记录与数据保护

“确认周记录”保存当时项目、人员顺序、版本、需求、任务、相关排期和投入等数据。后续修改实时数据不覆盖已有快照，再次确认生成新的确认版本。查看历史周记录时不可直接编辑。

变更记录保存时间、操作类型、对象、前后值和原因。业务状态修正、返工、取消、原计划修正等通过原因解释，避免丢失决策依据。清空需求最近变更有专门的数据操作，并在清理前备份；以后新增修改仍会继续产生记录。

周快照用于固定汇报版本；JSON 备份用于恢复整个研发管理数据。两者不互相替代。

保存采用修订号校验，避免两个浏览器互相覆盖。批量操作先验证最后的关联关系，再整批保存；写入失败尝试保留之前状态。被排期、投入或其他记录引用的对象，不能直接删除造成断链。

修改需求所属项目/版本时，关联排期、实际投入、关联期初会同步调整，工时和周次保持原值。共用工时的需求只能整组转移到同一归属，或先拆分共用范围；历史快照保持确认时的内容。

## 11. 日常维护顺序

1. 首次维护：人员及排序、项目及模块、专项版本。
2. 新功能：建立一次需求，选择所需角色任务、负责人、预计时长和计划周。
3. 安排未来工作：选择周次、人员、任务和预计小时，确认排期。
4. 周五复盘：核对本周实际内容与小时，确认角色完成情况，检查提前/延期，续排未完成事项。
5. 核对下周：去除已提前完成的工作，检查容量和草稿，确认下周目标。
6. 汇报：确认周记录，再导出固定版本的周工作表；重要调整前后可手动备份。

## 12. 当前边界与后续优先项

- 当前是单机维护，没有账号权限、云同步和团队分别填报。
- 提前量按周计算；没有工作日级提前量、奖金公式或自动奖励结算。
- 依赖与阻塞辅助提醒，不会根据容量自动替经理重新排期。
- 多轮测试、分批上线目前通过任务、日期和变更记录表达，没有专门的事件时间线。
- 部分目录归档后仍可能出现在历史筛选中；归档和永久删除需要继续明确区分。
- 后续最值得统一的是总览里程碑提醒与周排期口径，减少“已经完成但仍提醒”的理解成本。
